# Avoid low-value routing followed by a full analysis replay

Reported activity: an initial approximately 96,672-token prompt consumed 546,833 phase tokens, then a full-policy fallback with approximately 108,450 prompt tokens consumed another 492,214. The displayed total is exactly their sum, 1,039,047. Ten reported tools returned about 7,216 tokens; simply trimming result rows does not address the dominant prompt/replay cost. These are reported token totals, not a billing-price calculation.

The first implementation enabled routing for any positive character saving. With most business policy still classified as core, a small initial saving could be followed by a costly replay if the answer or initiative needed deferred policy. This guard requires at least 25% reduction of rendered skill instructions before enabling routing. The comparison includes semantic instructions, wrappers, exact-duplicate aliases and the deferred-section index. The threshold is a conservative engineering choice, not a prediction of fallback probability or a guarantee of token savings.

Below that threshold, all original policies reach the first analysis. There is no local skill library or policy-coverage fallback for that full-policy run. Other business/visual verification remains intact. The model, reasoning, history, memory and transaction checks are unchanged. Trace details include candidateSavingPercent, minimumSavingRatio and small_saving_full_context so this decision is visible.

This mitigates double analysis for marginal routing. It does not solve the roughly 100k-token base prompt, remove fallback when routing materially reduces context, or prove real answer quality. The next substantial reduction needs the actual production policy documents: consolidate overlapping merged skills, keep complete common constraints in a compact core, and map specialised policy by needs and conversational state. Unknown policy must not be discarded solely by filename. Original source locations have been requested from the user; production bodies are unavailable locally.

Validation: 13 routing/schema unit tests and 7 disposable-DB/provider-fixture pipeline tests passed, including a low-saving example which emits a payment answer in one full-policy analysis without a routing retry. Production build and scoped ESLint passed. No production service or paid AI call was used.
